# 구조

## 캔버스는 시각, DOM은 의미

접근성을 나중에 덧붙이지 않으려고 레이어를 처음부터 나눴다.

```
        게임 코어 (src/core)
     순수 TypeScript, 브라우저를 모른다
                 │
            이벤트 발행
     ┌───────────┼───────────┐
     ▼           ▼           ▼
  그림 레이어   의미 레이어   소리 레이어
 (src/render)   (src/ui)   (src/audio)
  Phaser 캔버스  시맨틱 HTML  Web Audio
  aria-hidden   ARIA live    HRTF 공간 음향
```

캔버스에는 `aria-hidden`을 붙여 보조기술에서 감춘다. 메뉴·대화·전투 UI는 진짜 DOM
버튼과 목록으로 만들기 때문에 키보드 조작과 스크린리더 지원이 따라온다. 게임에서
일어나는 모든 사건은 코어가 이벤트로 발행하고, 세 레이어가 각자 구독해 자기 방식으로
표현한다. 하나의 상태, 세 개의 렌즈다.

## 게임 코어의 순수성

`src/core`는 Phaser도 DOM도 `window`도 모른다. 타이머조차 바깥에서 주입받는다.

```ts
new Game(data, bus, {
  schedule: (fn, ms) => window.setTimeout(fn, ms),
  cancel: (handle) => window.clearTimeout(handle as number),
})
```

이렇게 두면 세 가지가 가능해진다. 노드에서 그대로 유닛 테스트할 수 있고, 멀티플레이가
턴 진행을 원격 신호로 바꿔 끼울 수 있고(실제로 그렇게 했다 — 아래 "함께 하기" 절),
언젠가 다른 엔진으로 옮기더라도 규칙은 그대로 살아남는다.

행동의 유효성 검사도 UI가 아니라 코어가 한다. 내 차례가 아니거나 쿨다운 중인 요청은
코어가 거부한다 — 버튼 비활성화에만 기대면 원격 입력이 들어오는 순간 구멍이 된다.

## 함께 하기 — 결정적 코어가 동기화의 토대다

이 게임에는 무작위가 없다. 접근성을 위해 내린 결정("셀 수 있는 규칙")이 멀티플레이의
구조를 공짜로 만들었다 — 같은 명령 열을 재생하면 모든 화면이 같은 세계에 도달하므로,
오가는 것은 상태가 아니라 **명령**뿐이다.

```
게스트: 제안(propose) ──▶ 방장: 전역 번호를 붙여 확정(apply) ──▶ 전원이 같은 순서로 재생
```

- 방장의 화면도 특별하지 않다. 자기 명령조차 확정 순서를 지나야 적용되므로, 화면마다
  적용 순서가 갈리는 일이 구조적으로 불가능하다
- 턴 사이의 자동 진행(타이머)도 명령이다. 시계는 방장 하나만 돌리고, 만료를 명령으로
  순서화한다 — 원격 명령과 타이머 만료의 경합이 사라진다
- 자리(좌석)마다 조작자가 있다. 연결이 끊긴 자리는 동료 AI가 즉시 이어받는다 —
  솔로에서 동료가 스스로 싸우던 코드가 그대로 대행이 된다
- 이동과 대화 넘김은 길잡이 한 사람이 쥔다. 지목해서 넘긴다 — 제일 느린 사람의 속도가
  파티의 속도가 되도록
- 세 렌즈(그림·글·소리)는 원격 동료의 행동에 추가 작업이 필요 없었다. 코어가 내는
  같은 이벤트를 구독할 뿐이기 때문이다. "나"의 기준만 화면마다 다르게 주입했다

솔로 플레이는 이 모든 것을 모른다. UI와 게임 사이의 문이 세션 없을 때는 호출을
그대로 통과시키고, 네트워크 코드는 "함께 하기" 버튼을 누를 때에만 동적으로 불려 온다 —
혼자 하는 실행에는 외부 요청이 한 건도 없다.

### 보안 — 피해 반경으로 방어한다

정적 호스팅과 관리형 백엔드 위에 있으므로 서버 권위가 없다. 모든 공격을 막는 대신
피해가 미치는 반경을 층으로 나눴다.

- **계정·선물·저장(데이터베이스)**: 행 단위 권한(RLS)이 지킨다. 남의 저장과 선물에는
  닿을 수 없고, 선물 수령은 서버가 1회만 허용하며, 계정당 하루 상한이 있다
- **세션 채널**: 초대 코드는 헷갈리는 글자를 뺀 40비트이고, 로그인한 사람만 채널에
  닿는다. 좌석 없는 제안·남의 좌석 사칭·방장 전용 명령·재전송·폭주는 방장이 버린다.
  원격에서 온 페이로드는 전부 런타임 타입 가드를 지나야 하고, 통과하지 못하면 조용히
  버려진다. 그래도 세션 안의 위조를 완전히 막을 수는 없다 — 이 피해는 그 세션의 화면을
  넘지 못하고, 상태가 매듭지어질 때마다 검증 합계를 비교해 어긋나면 방장의 기록으로
  되맞춘다. 협동 전용이고 경쟁·순위가 없어 위조의 이득 자체가 없다는 것이 마지막 층이다
- **자기 계정 조작은 위협 모델 밖이다**: 로컬 저장은 원래 본인 소유다. 경쟁 요소를
  도입한다면 그때는 서버 쪽 검증 계층이 필요하다 — 그 경계를 알고 있다

## 데이터 주도

직업 능력치, 몹, 스킬, 스테이지 지도, 대사, 파티 구성이 전부 `src/data`의 JSON이다.
스킬은 종류(`kind`)와 대상(`targeting`)을 데이터로 갖기 때문에, 새 스킬을 넣을 때
코드에 분기를 추가하지 않는다.

밸런스를 코드에서 분리해 두면 나중에 관리 도구에서 수치를 조정할 수 있고, 엔진을
바꾸더라도 데이터는 그대로 옮겨 간다. 특성도 마찬가지로 `traits.json`에 있고, 화면에
보이는 이득·대가 문장은 그 수치에서 조립한다.

## 지각 범위는 렌더러가 아니라 코어가 소유한다

"좁은 지각" 특성을 만들면서 배운 것이다. 캔버스에만 안개를 걸면 낭독과 텍스트 기록으로
정보가 그대로 새어 나간다. 그래서 코어의 `Field.isKnown(위치)`가 "무엇을 아는가"를
결정하고, 세 렌즈가 모두 그 판정을 통과한다. 나중에 몹 위치를 알리는 소리를 추가하더라도
같은 판정을 거치면 된다 — 렌즈를 늘려도 누수 지점이 생기지 않는다.

## 리소스

외부 이미지·사운드 파일을 쓰지 않는다. 스프라이트는 픽셀 배치 데이터로 두고 실행 시
캔버스에 그리며, 효과음은 Web Audio로 합성한다. 라이선스를 따질 일이 없고, 저자극
모드의 낮은 채도 팔레트도 같은 데이터에서 계산해 낸다. 자세한 내용은
[CREDITS.md](../CREDITS.md)에 있다.

## 배포

정적 파일만 나오므로 GitHub Pages에서 그대로 돌아간다. main에 푸시하면 GitHub
Actions가 테스트를 돌리고, 빌드해서 배포한다. 빌드 잡은 외부 의존성 코드를 실행하므로
읽기 권한만 갖고, 배포 권한은 배포 잡에만 준다.

## 앞으로

- **좌석별 특성**: 지금은 방장의 특성 하나가 세계에 적용된다. 자리마다 다른 특성을
  가지면 "각자 다른 렌즈"가 규칙 차원에서 완성된다 — 좁게 보는 사람에게 넓게 보는
  동료가 알려 주는 협동이 여기서 나온다. 저장 형식에 자리별 특성을 더하는 좁은 작업이라
  다음 우선순위로 둔다
- **스테이지 추가**: 지도·조우·대사가 전부 데이터라 JSON 파일을 늘리면 된다.
  실제로 스테이지 2·3을 그렇게 추가했다 — 배열 순서가 진행 순서이고, 스테이지끼리
  서로를 참조하지 않는다
- **계정 동기화**: 저장 자리는 `SaveRepository` 인터페이스 뒤에 있다. 화면은 그 인터페이스만
  알기 때문에, 클라우드 구현을 하나 더 만들어 끼우면 사용자가 겪는 흐름은 그대로다.
  세 칸이라는 단위도 동기화의 비교 단위로 그대로 쓰인다
- **경쟁 요소를 넣게 된다면**: 지금의 신뢰 모델은 협동 전용이라 성립한다. 순위나 보상이
  걸리는 순간 서버 쪽 검증(함수 계층)이 필요하다는 것을 한계로 적어 둔다
